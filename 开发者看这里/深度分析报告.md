## 第一章 · 项目本质：这种软件要解决什么问题

### 1.1 本质抽象

Wallpaper_Notes 本质上是一个**双向同步的渲染管道**：

```
文件系统（.md 文件）
    ↕ 实时同步（watchdog 监听 + 手动写入）
GUI 视图层（QTextBrowser / QPlainTextEdit）
    ↕ 用户操作（双击编辑、快捷键唤出）
用户意图（记录、提醒、灵感捕捉）
```

这个管道的核心设计原则是**文件系统是唯一的真相源（Source of Truth）**：

- 用户用 GUI 编辑 → 写入 `.md` 文件
- AI/外部脚本写入 `.md` 文件 → GUI 自动刷新
- 二者通过文件系统自然同步，没有额外的状态同步层

### 1.2 与其他便签工具的本质区别

| | Wallpaper_Notes | Obsidian | Windows Sticky Notes |
|---|---|---|---|
| **显示层级** | 桌面层（壁纸之上） | 普通窗口层 | 普通窗口层 |
| **编辑摩擦** | 双击/快捷键 | 需打开软件+切换 | 需双击任务栏图标 |
| **真相源** | 文件系统（.md） | 自有数据库 | 自有数据库 |
| **AI友好度** | 极高（直接读写文件） | 需插件 | 无 |

所以这个产品的本质不是一个"功能丰富的编辑器"，而是一个**"极低摩擦的桌面信息显示面板"**——花里胡哨的功能不是目标，**"打开电脑就看到"** 才是。

## 第二章 · 每个模块的深度用意分析

### 2.1 `main.py` — 进程入口（20 行）

**用意：** 作为整个应用的启动点，创建 QApplication 并实例化 App 控制器。

**为什么这么设计：**
- 把 `App` 的构造参数（目录路径、配置路径）放在 main.py 中，而不是硬编码在 App 内部
- 这样做的好处是：未来如果改成从命令行参数读取配置，或者支持多实例，只需改 main.py

**当前状态：** ✅ 稳定，无需改动

---

### 2.2 `app.py` — 应用生命周期控制器（130 行）

**用意：** 作为所有模块的"总装车间"——初始化、接线、清理。

**设计决策分析：**

1. **模块创建顺序有严格的依赖关系：**
   ```
   Config → Window（需要 Config, Theme）→ NotesManager → Hotkey → Tray
   ```
   Hotkey 的注册延迟到 `run()` 中 window.show() 之后，因为需要有效的 HWND。

2. **为什么用 callbacks 而不是信号连接 Window → NotesManager：**
   Window 不直接引用 NotesManager，而是通过 `self._callbacks["on_save_content"]` 这种函数表。这样 Window 不需要 import NotesManager，实现了接口解耦。代价是缺少类型检查。

3. **为什么 _load_custom_fonts 在 Window 之前执行：**
   字体需要先注册到 QFontDatabase，Window 创建时设置的字体才能正确解析。

**值得注意的设计权衡：**
- `_on_settings_requested` 中重新调用 `self._config.load()` 重新加载 theme.json——这是因为设置对话框可能被外部修改覆盖了 theme.json，需要保证 UI 展示的是最新值。但也意味着设置对话框打开时有 IO 操作。
- `self._hotkey.activated` 连接了两个 lambda——一个 `print` 调试，一个实际功能调用。**这是调试残留，deubg lambda 应该移除**。

**当前状态：** ⚠️ 结构清晰，但有调试打印残留和轻微逻辑冗余。

### 2.3 `window.py` — 桌面窗口管理器（620 行，最复杂）

**用意：** 管理窗口的所有视觉行为和用户交互——窗口层级、标签系统、编辑模式切换、拖拽缩放、特效渲染。

**核心矛盾分析：**

#### 2.3.1 `WA_TranslucentBackground` — 这行代码是整个窗口视觉系统的起点

```python
self.setAttribute(Qt.WA_TranslucentBackground)
```

**为什么需要它：** 没有这一行，窗口背景就是纯色矩形块，无法半透明透出桌面壁纸。

**它带来了什么代价：**
1. 所有子控件的默认背景都是透明的
2. Windows 原生窗口的圆角（QSS `border-radius`）在分层窗口中不生效 → 只能用 `setMask(QPainterPath)` 剪切实现圆角
3. Windows 会拦截透明区域的鼠标事件 → 必须用 `WM_NCHITTEST` 返回 `HTCLIENT` 强制接收
4. 颜色叠加变得反直觉——半透白色背景上叠加透明标签栏、透明文字区域，最终视觉颜色不能直接用 "theme.json 里的值" 推算

**这是整个视觉系统"不可预测感"的根源。**

#### 2.3.2 QSS 注入：三层覆盖

Window 的样式应用有三层：

| 层级 | 来源 | 影响范围 | 优先级 |
|---|---|---|---|
| 第一层 | `build_global_qss()` → `self.setStyleSheet()` | 所有子控件 | 低（被子控件覆盖） |
| 第二层 | `viewer.setStyleSheet(generate_content_qss())` | viewer 单独 | 中 |
| 第三层 | `QStackedWidget.setStyleSheet(...)` 独立注入边框+玻璃 | stack 单独 | 高 |

**问题：** `build_global_qss()` 中已经包含了 `generate_content_qss` 和 `generate_editor_qss`，然后又被子控件的局部 `setStyleSheet` 覆盖了。全局中的 content/editor QSS 是**无效的冗余代码**。

#### 2.3.3 鼠标事件：三套机制的协作

| 机制 | 监听什么 | 处理什么 | 谁先触发 |
|---|---|---|---|
| `nativeEvent` | WM_NCHITTEST | 强制全区域 HTCLIENT | Windows 消息级别，最先 |
| `eventFilter` | 子控件事件 | 双击编辑、三击退出、标签栏拖拽、按键 | Qt 事件过滤器 |
| `mousePressEvent` | 自身事件 | 边缘缩放检测 | 自身事件处理 |

三种机制各管一摊，边界还算清晰。`nativeEvent` 返回 HTCLIENT 后，Windows 把所有鼠标事件都传给 Qt，Qt 再分流到 eventFilter 和 mousePressEvent。

**但有一个微妙问题：**
- 标签栏/⊕ 按钮区域既触发 eventFilter 的拖拽逻辑，又是 QTabWidget 原生的点击切换逻辑
- eventFilter 中用 `manhattanLength()` 距离阈值区分"点击"和"拖拽"
- 但鼠标点击在标签上触发切换，如果要拖拽窗口，需要先按住标签再拖动
- 这可能导致：用户想点击切换标签时，如果鼠标有微小移动，被判定为"拖拽"而阻止了切换

#### 2.3.4 编辑模式三击退出机制

```python
self._edit_dblclick_count: int = 0
# ...
if etype == QEvent.Type.MouseButtonDblClick and editing:
    self._edit_dblclick_count += 1
    self._edit_dblclick_timer.start(QApplication.doubleClickInterval())
    if self._edit_dblclick_count >= 2:  # 2 次 DblClick = 3 次物理点击
```

用意：在编辑模式下连续三击鼠标（2 个双击事件 + 1 个点击）退出编辑。

**潜在问题：**
- 双击事件发生在第二次物理点击时。所以 "2 次 DblClick" 对应的是第 2 次和第 4 次物理点击，实际上需要 4 次物理点击才能触发。
- 不对，我来重新理解：双击事件一次触发 = 第二次物理点击。所以第 1 次 DblClick 事件 = 物理第 2 次点击，第 2 次 DblClick 事件 = 物理第 4 次点击。
- `QApplication.doubleClickInterval()` 是两次双击之间允许的最大间隔，默认约 400ms。
- 也就是说用户需要在 400ms 内完成 4 次物理点击（或 3 次物理点击，取决于第一次单点是否被识别为双击的一部分）... 这其实挺难做到的。

**实际上这个三击设计可能是有Bug的。** 代码注释写的是"2 次 DblClick = 3 次物理点击"，但实际上 DblClick 事件已经是第 2 次物理点击了。所以 2 次 DblClick = 第 4 次物理点击。

但文档（PRD）和 README 都写的是"三击退出"——实际需要四击，这是一个文档与实现的不一致。

#### 2.3.5 特效的实现策略

| 特效 | 实现方式 | 性能成本 |
|---|---|---|
| 玻璃效果 | QSS `qlineargradient` 半透渐变背景 | 极低（GPU 光栅化） |
| 文字辉光 | QGraphicsEffect + box blur 缩小放大 | 中（每个 text block 都需重绘） |
| 磨砂噪点 | QWidget + QPainter 随机灰度绘制 + 150ms resize 防抖 | 中（重绘频繁时） |

设计决策分析：
- 玻璃效果用 QSS 而非真正的 Windows 模糊（如 `DwmExtendFrameIntoClientArea`）——因为后者在 Windows 10/11 上的表现不稳定，且对不同壁纸颜色的适应性差
- 磨砂噪点的 resize 防抖（150ms）是有意为之的性能优化——拖拽缩放时只拉伸旧缓存，停稳后才重新生成噪点

**当前状态：** ⚠️ 核心文件，设计思路清晰但实现细节存在多处问题

### 2.5 `renderer.py` — Markdown 渲染管道（140 行）

**用意：** 不用 QTextBrowser 的内置 Markdown 解析器，而是自己造一个。

**为什么不用 QTextBrowser.setMarkdown() 而自己写：**
- Qt 的 Markdown 解析器是 C++ 层的黑盒，对空行、列表嵌套的处理经常不符合预期
- 自建解析器可以对渲染效果做精确控制（字体、颜色、间距）
- 完全控制 CSS 注入，可以将 theme.json 的内容样式精确应用到渲染结果

**设计决策：**
- 只实现了 Markdown 的最小子集（标题、段落、列表、引用、行内粗体/斜体/代码）——这是故意的，因为产品的核心是"展示"而不是"撰写复杂文档"
- HTML 通过 `QTextBrowser.setHtml()` 注入，CSS 内联在 `<style>` 标签中
- 不支持图片、表格、代码块语法高亮等——超出 MVP 范围

**当前状态：** ✅ 职责清晰，边界明确，稳定

### 2.6 `notes_manager.py` — 文件系统映射器（170 行）

**用意：** 将 `notes/` 目录映射为标签列表，监听文件变化。

**设计决策：**

1. **为什么用 `PollingObserver` 而不是 `Observer`（原生文件系统通知）：**
   Windows 上的原生文件系统通知（`ReadDirectoryChangesW`）在网络驱动、移动硬盘等场景下不稳定。`PollingObserver` 是轮询，跨平台兼容性好，代价是有 300ms 的检测延迟。

2. **防抖机制：**
   ```python
   _DEBOUNCE_MS = 300
   key = (event_type, str(path_obj.resolve()))
   ```
   用事件类型+路径的元组做 key，记录最近一次时间戳。同类型同路径的事件 300ms 内重复触发被忽略。避免了 watchdog 在文件写入过程中多次触发 `modified` 事件。

3. **create 方法与 watchdog 的协作：**
   ```python
   def create(self, filename: str) -> NoteInfo:
       filepath.write_text("", encoding="utf-8")  # 写文件
       # watchdog 会检测到这次创建 → 发射 note_added
       self.note_added.emit(str(filepath))        # 又手动发射一次
   ```
   **这里手动发射是有意的还是 bug？** 看代码注释 ——"由于是自己创建的文件，watchdog 会检测到。但我们用防抖来避免重复通知。" 

   实际上这里的设计是：`create()` 同时通过文件 IO 和手动信号来通知。但 watchog 线程和 Qt 主线程之间的时序不确定，可能手动信号先到，也可能 watchdog 信号先到。而 `window.add_tab` 中有重复检查（`_find_tab_index`），所以不会重复添加，但会产生一次执行了一次return的无效调用。

   更好的设计是：create 方法不发射信号，让 watchdog 自然检测到文件变化后发射信号。

**当前状态：** ⚠️ 功能正确，但 create 的信号发射存在逻辑浪费

### 2.8 `hotkey.py` — 全局热键注册器（150 行）

**用意：** 用 Windows API 注册系统级快捷键，不依赖任何第三方库。

**设计决策：**

1. **为什么不用 Qt 的 `QShortcut` 或 `QHotkey`：**
   - `QShortcut` 只在应用获得焦点时有效，失去焦点就收不到
   - `QHotkey` 是第三方库，需额外依赖
   - Windows API `RegisterHotKey` 是系统级快捷键的标准方式

2. **`MOD_NOREPEAT` 标志：**
   添加这个标志后，按住热键不放只触发一次 `WM_HOTKEY`，不会重复触发。这是关键的用户体验优化——避免按住快捷键时窗口反复闪烁。

3. **MSG 结构体的兼容处理：**
   ```python
   msg_addr = int(message)  # 兼容 PySide2（int）和 PySide6（sip.voidptr）
   ```
   这一行兼容了不同的 PySide 版本。

4. **`_get_hwnd()` 的 HWND 获取策略：**
   优先用 `activeWindow()`，回退 `topLevelWidgets()[0]`。在 `window.show()` 之后调用，确保 `activeWindow()` 有效。

**当前状态：** ⚠️ 功能正确，但有大量的 debug print 残留

## 第三章 · 冲突分析

### 3.1 冲突一：配置语义与实际视觉效果的不匹配（严重）

**症状：** 用户调节"窗口背景色"和"标签栏背景色"时，实际改变的视觉区域与用户预期不符。

**根源分析：**

```
用户预期                    实际控制
┌─ 窗口样式 → 背景色 ──┐   ┌─ WallpaperWindow 的 background-color ────┐
│  控制整个窗口颜色      │   │  影响：窗口边框周围 + QTabBar透出（标签行）│
└───────────────────────┘   └──────────────────────────────────────────┘

┌─ 标签栏 → 背景色 ─────┐   ┌─ QTabWidget::pane 的 background-color ──┐
│  控制标签按钮行的颜色   │   │  影响：内容面板区域（标签栏下面的方框）    │
└───────────────────────┘   └──────────────────────────────────────────┘

┌─ 内容区 → 背景色 ─────┐   ┌─ QTextBrowser 的 background-color ──────┐
│  控制文字背后的颜色     │   │  实际被 glass 层部分遮挡，视觉权重不一   │
└───────────────────────┘   └──────────────────────────────────────────┘
```

**为什么会这样：** 这个冲突不是 bug，而是 `WA_TranslucentBackground` + QTabWidget 的组件结构 + 三层 QSS 注入 + 各层 alpha 混合共同导致的**系统级视觉复杂性**。每一个设计决策单独看都是合理的，但组合起来产生了反直觉的效果。

**修复方向：** 给 QTabBar 加背景色，让标签栏和内容面板的颜色独立可调。

### 3.2 冲突二：全局 QSS 与局部 QSS 的冗余（中优先级）

**症状：** `build_global_qss()` 中包含了 `generate_content_qss()` 和 `generate_editor_qss()` 的输出，但 window.py 中又对每个 viewer 和 editor 单独调用 `setStyleSheet()` 覆盖了全局设置。

**原因：** 全局 QSS 是在 Window 初始化时一次性设置的，而 viewer/editor 的局部 QSS 在每次创建/刷新时设置。后者覆盖前者，全局中的 content/editor 样式从未生效。

**影响：** 性能损失极小（字符串拼接 + QSS 解析），但增加了代码理解成本——新人读代码时难以判断哪条 QSS 真正生效。

**修复方向：** 从 `build_global_qss()` 中移除 `generate_content_qss()` 和 `generate_editor_qss()` 的调用。

### 3.3 冲突三：notes_manager.create() 的双重通知（低优先级）

**症状：** 调用 `create()` 后，既手动发射 `note_added` 信号，又通过 watchdog 检测到文件创建后再次发射同一信号。

**原因：** 代码中同时使用了两种通知机制，通过防抖去重。虽然 `window.add_tab` 有重复检查不会造成实际双重添加，但信号链路做了无用功。

**修复方向：** create 方法中不手动发射信号，让 watchdog 自然检测。但需要注意：watchdog 是异步的（300ms 防抖），create 返回时标签不会立即出现在窗口中。可以改为：create 直接调用 `add_tab` 的回调。

### 3.4 冲突四：四击退出 vs 三击退出（低优先级）

**症状：** 代码实现需要 4 次物理点击才能退出编辑模式（2 次 DblClick 事件），但 README/PRD 都写着"三击退出"。

**原因：** `QMouseEvent::MouseButtonDblClick` 在第二次物理点击时触发。所以：
- 第 1 次 DblClick = 物理点击 2
- 第 2 次 DblClick = 物理点击 4
- 需要 4 次物理点击才能达到 `_edit_dblclick_count >= 2`

**修复方向：** 把阈值改为 `>= 1`（单次双击事件 = 三击），或者重新设计为：在编辑模式下检测 `MouseButtonPress + MouseButtonDblClick` 组合。

## 第六章 · 总结

### 项目成熟度评估

| 维度 | 评级 | 说明 |
|---|---|---|
| **架构设计** | ⭐⭐⭐⭐ | 模块划分清晰，职责边界明确，文档完善 |
| **用户体验** | ⭐⭐⭐ | 基本功能可用，但配置系统的语义混乱影响自定义体验 |
| **代码质量** | ⭐⭐⭐ | 主体代码整洁，但调试残留和冗余 QSS 破坏了整洁度 |
| **稳定性** | ⭐⭐⭐⭐ | 核心功能稳定，边缘缩放/拖拽/热键工作正常 |
| **可维护性** | ⭐⭐⭐ | 文档和架构设计完善，但逻辑冗余增加了理解成本 |

### 最核心的洞见

Wallpaper_Notes 的代码质量整体高于大多数 MVP 项目。其最大的设计成就——也是最大的设计负担——就是 **WA_TranslucentBackground**。这一行代码让便签能够优雅地融入桌面，但也让颜色体系变得不可直观预测。

如果把项目比作一栋建筑：

- **地基**（架构设计、模块划分）非常坚固
- **结构**（文件监听、窗口管理、渲染管道）逻辑清晰
- **装修**（主题系统、设置界面）出现了"墙纸颜色→实际粉刷到不同房间"的语义错位

**修复的核心方向不是加功能，而是让已有的功能匹配它在界面上的语义。** 标签栏背景色就是最典型的例子——不是功能缺失，是语义映射放错了位置。
